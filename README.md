# Fraud Analytics Portfolio

Four projects that practice the core work of a fraud analytics team: SQL analysis, rule testing, metric design, data-quality monitoring, and abuse detection.

**Data note:** all data is **simulated** by `data/generate_data.py` (a fantasy-sports-style platform with about 59K accounts, 156K deposits, promos, entries, and withdrawals). It is not real company data. Fraud patterns were built into the simulation on purpose, so results show the method working, not real-world findings.


## Projects

| # | Project | What it shows | Headline result (simulated data) |
|---|---|---|---|
| 1 | [SQL fraud analysis](01_sql_fraud_analysis/) | Joins, CTEs, window functions (ROW_NUMBER, LAG, running sums) | Disposable-email accounts and devices shared by 5+ accounts are the strongest fraud signals |
| 2 | [Fraud vs. friction backtest](02_fraud_vs_friction_backtest/) | Point-in-time features, train/holdout split, tradeoff analysis, sensitivity testing | Chosen rule caught 52% of fraud accounts and 65% of fraud dollars while flagging 0.38% of legitimate users on holdout |
| 3 | [Dashboard and metric dictionary](03_dashboard_metric_dictionary/) | Metric definitions, mature-cohort reporting, anomaly detection | Flagged a 12-hour logging outage and a duplicate-event spike |
| 4 | [Multi-account ring detection](04_multi_account_detection/) | SQL self-joins, union-find clustering, precision/recall tradeoff | Device links found 76% of ring accounts with no false flags; adding IP links flagged 454 innocent accounts |

## Run it

```bash
pip install -r requirements.txt
cd data && python3 generate_data.py                 # builds fraud.db (about 5 seconds)
cd ../01_sql_fraud_analysis && python3 run_queries.py
cd ../02_fraud_vs_friction_backtest && python3 backtest.py
cd ../03_dashboard_metric_dictionary && python3 build_dashboard.py   # writes dashboard.html
cd ../04_multi_account_detection && python3 detect_rings.py
```

Each project folder includes its code and a `results.md` generated by the script. Project 3 also writes CSVs that can be loaded into Tableau Public or Looker Studio.

## Limitations (stated up front)

- The backtest assumes a flagged fraud account's entire loss is prevented, and that manual-review labels cover about 92% of true fraud. Both flatter the rule. A real team would confirm with an A/B holdout.
- Friction cost assumptions (share of flagged users who churn, value of a legitimate user) are guesses; the sensitivity table shows the chosen rule does not change across a wide range.
- Perfect device-link precision in Project 4 is an artifact of the simulation. Real data would be messier.
